## 零、初学者先读：从句子到图谱，三部曲的最后一块拼图

> 2026-11-06 新增的教学补充。首次学习先读本节，再进入后面的公式、原课代码与纠错。本课是“信息抽取三部曲”的收官：[第06课](<06：命名实体识别——BIO、规则、CRF与神经模型.md>)找出实体名字，[第24课](<24：共指消解——提及、先行词、聚类与跨句实体.md>)把名字和代词归成同一个实体，[第25课](<25：实体链接与消歧——候选、上下文、知识库与NIL.md>)给实体挂上知识库稳定ID，本课在挂了ID的实体之间**抽关系、连成图**——节点来自前两课，边是本课的产出。

### 0.1 先理解这一课在做什么

原课的例子：“Tim Cook became CEO of Apple in 2011”一句话能拆出四条事实：(Tim Cook, role, CEO)、(Tim Cook, employer, Apple)、(Tim Cook, start_date, 2011)、(Apple, type, Organization)。把自由文本变成这种结构化的(s, r, o)三元组，再整批堆进一个库，就得到知识图谱——它是RAG、分析和合规审计的推理底座。2026年的新麻烦是LLM抽关系“太热情”：会编出原文不支持的貌似合理的虚构（幻觉三元组），没有溯源（出处）就分不清真事实和假故事。所以本课有一半篇幅在讲“怎么验收一条边”。

类比：前两课像办婚礼前的资料整理——NER数请柬上的名字，共指确认“小王、新娘表哥、他”是同一个人，EL在户籍系统里查到身份证号；本课记录“谁和谁是什么关系”——(小明, 就职于, VW)。注意：**只有节点的图只是通讯录**，能回答问题的是边——“谁在VW上班”要顺着P108这条边查。而边最要命的两个属性是方向（就职于谁）和出处（哪份文件第几行说的）——方向反了查询答错人，出处缺了出错无法追溯。

### 0.2 本课术语先翻成白话

- 三元组（triple）=(subject, relation, object)，图的原子单位，一条边
- 本体（ontology）=关系类型的“户口簿”：允许哪些关系ID、各是什么方向
- 开放IE（Open IE）=关系随便写（任何动词短语都能当关系），召回高、难查询
- 闭合本体=关系ID固定（如Wikidata的P108、P112），可查询、难编造
- 规范化（canonicalization）=把“就职于/在……上班/服务于”统一映射到P108，并确认方向
- AEVS=锚定（Anchor）→抽取（Extract）→验证（Verify）→补覆盖（Supplement），2026年的抗幻觉流水线
- 溯源（provenance）=每条事实带文档ID、字符区间、引文、版本、抽取器、时间
- 限定符（qualifier）=挂在边上的时间等条件：“2011年起任CEO”
- 远程监督（distant supervision）=拿现成KB对齐文本自动生成弱标签
- P108=employer（雇主，声明挂在雇员身上）；P112=founded by（创立者，声明挂在公司身上——**方向要反转**）；P19=place of birth；P169=CEO

### 0.3 用小数字走一遍

两句话、一条边、一次方向反转，把“锚定→抽取→规范化→画图”走一遍（算例）：

~~~text
句1：小明就职于VW。      小明 span [0,2)，VW span [5,7)
句2：他的工号是001。      “他”要先过第24课的共指解析回“小明”，才挂得上边
~~~

**第一步：锚定（Anchor）。** 句1的实体span：text[0:2]="小明"✓、text[5:7]="VW"✓——区间可纸笔复核。句2的“他”字符串本身不含身份，锚定前必须先共指；工号是属性，不构成实体间的边。

**第二步：抽取（Extract）。** 从句1抽出开放三元组（小明, 就职于, VW）。

**第三步：规范化到闭合本体。** 把“就职于”映射到Wikidata的P108（employer）。关键动作是**查属性方向**：P108的声明挂在雇员身上，所以：

~~~text
正确：小明 ──P108(雇主)──▶ VW     读作：小明的雇主是VW
错误：VW ──P108(雇主)──▶ 小明     读作：VW的雇主是小明
                                   ↑格式完全合法，语义正好反向
~~~

**方向错误示范（正文2.9的原例）。** 从“Bob founded Beta”抽到(Bob, founded, Beta)，映射P112时必须换向成(Beta, P112, Bob)——因为Wikidata的P112叫“founded by”，声明挂在**公司**身上。只把关系名换成P112、主宾不动，得到的是格式正确、语义反向的图——查询“谁创立了Beta”会答错人。这类错误增大模型不能自动消除，要靠本体契约（映射表写明方向）和单元测试（第五节的canonical_triple就内置了方向处理）。

**第四步：画图（2节点、1条边）并挂档案。**

~~~text
   ┌──────┐   P108    ┌────┐
   │ 小明 │ ─────────▶ │ VW │
   └──────┘   就职于    └────┘
   边的档案：{doc_id, 实体span (0,2)/(5,7), 引文“小明就职于VW”, 抽取器版本, 时间}
~~~

一条没有档案的边，出了错无法追责；一条有档案的边，可审计、可撤销——这就是provenance。

以上是用于理解的算例，不是新增的训练或性能实测。

### 0.4 怎样连接到正文代码

四段代码对应三步加存储：4.1的PATTERNS是规则路线的模板（0.3第二步的自动化版，但原正则只认ASCII大写开头的单词，中文和多词名都不匹配——正文纠错点）；4.2的REBEL是神经路线，输出带`<triplet>`标记要按模型卡协议解析，不能把decoded字符串直接当图边；4.4的RELATION_MAP+canonicalize做0.3第三步的规范化（原课“is the CEO of”大写key永远对不上的bug，正文有纠错）；4.5的neighbors在图上查询。第五节的extract+canonical_triple是可运行的最小闭环：extract跑PATTERNS，canonical_triple把worksAt→P108、founded→(Beta, P112, Bob)反转——0.3第三、四步的结论可以直接用它核对。

### 0.5 理解检查（含参考答案）

**问题1：** 为什么“字符span一致”不等于“关系成立”？

**参考答案：** span验证只证明文字确实出现在原文（锚点对），不证明语义关系为真——“Alice did not found Acme”两个名字都锚得住，但关系是否定的；传闻、假设、时态错配同理。所以验证要过语义关，不只对字符（正文第七节1条）。

**问题2：** “Tim Cook became CEO of Apple in 2011”里的2011年应该放进哪条三元组？

**参考答案：** 作为限定符（qualifier）挂在任职事实上——(Tim Cook, P169, Apple)带起始时间2011；而不是无上下文的全局属性(person, start_date, 2011)。时间限定的是这条边，不是这个人。

**问题3：** 开放IE和闭合本体各拿什么换什么？

**参考答案：** 开放IE拿可查询性换召回——任何动词短语都能当关系，但“was born in / came from / is a native of”是三个不同的关系ID；闭合本体反过来，可查询、难编造，但要付规范化成本（原课参考：占工程时间60%～80%）。生产图常混用：开放IE做发现，规范化后并入主图。

## 一、这一课解决什么问题？

识别实体后，还要从来源中抽出实体之间的关系。知识图谱不只是(s,r,o)列表，还需要方向、来源、时间、规范ID与可撤销的合并记录。

## 二、核心概念与推导

三元组(subject,relation,object)构成图的边。规则/Hearst模式可解释但窄；监督分类预测实体对关系；REBEL等seq2seq生成三元组；LLM抽取灵活但可能编造或误读。

（补充 2026-11-06）把三部曲的分工画清楚，才知道本课站在哪里：

| 环节 | 产出 | 出错的代价 |
|---|---|---|
| NER（[第06课](<06：命名实体识别——BIO、规则、CRF与神经模型.md>)） | 实体提及 | 边的端点就是错的 |
| 共指（[第24课](<24：共指消解——提及、先行词、聚类与跨句实体.md>)） | 文档内实体簇 | “他创立了X”被挂到别人头上 |
| EL（[第25课](<25：实体链接与消歧——候选、上下文、知识库与NIL.md>)） | KB稳定ID | 同一实体的边散在两个节点 |
| RE（本课） | (s, r, o)边 | 图上多、少、反向一条边 |

“图的原子是边不是节点”：节点堆没有查询价值，(小明, P108, VW)这条**有方向的边**才是能回答问题的最小单元。方向反了（零节0.3的VW→小明），图在形式上依旧合法、查询照常跑，答案却换了人——这是比缺一条边更隐蔽的错误，因为它不报错。三条抽取路线对照：

| 路线 | 怎么干 | 强项 | 弱项 |
|---|---|---|---|
| 规则/Hearst | “X such as Y”→(Y, isA, X) | 精准、可调试 | 覆盖窄、脆 |
| 监督分类 | 对句中实体对预测关系 | 有标注数据时稳 | 领域迁移要重训 |
| 生成（REBEL/LLM） | 直接生成三元组 | 灵活、开箱即用 | 会编造，需锚定+验证兜底 |

三者在0.3的第二步可以互换，但第四步的档案（溯源）对三条路线一视同仁——没有出处就不许进图。

开放IE允许自由关系短语，闭合本体限制关系ID及类型。规范化不仅改名字，还要确认主客体方向、实体类型、否定和时间。例“某人2011年开始担任公司CEO”的日期应限定任职事实，而非全局(person,start_date,2011)无上下文属性。

（补充 2026-11-06）“规范化不只是改名字”值得配一张清单。设句子“Bob在2011年加入Beta后创立了Gamma”，粗抽得到(Bob, 加入, Beta)、(Bob, 创立, Gamma)两条开放三元组；规范化要逐条过五关：①关系ID——“加入”映射P108还是P112（若他是创始人）？②方向——P112要换向（正文2.9的Beta例子）；③实体类型——P112的主语应是组织，主语是人就可疑；④否定与模态——“计划创立”不是“已创立”；⑤时间限定——“2011年”挂哪条边上。原课参考：这类工作占图谱工程时间的60%～80%——因为每个关系属性都要人工核方向和语义，模型再大也不会自动消失。

原课以AEVS命名锚定→抽取→验证→补覆盖。它是一个来源中的设计，不是所有关系抽取的统一标准。字符span一致只证明文字确实出现，不证明该关系成立；否定、传闻、假设与主体错配仍需语义校验。

（补充 2026-11-06）AEVS四步用“带凭证的报销”类比最直观：Anchor像把每张发票贴到具体日期和项目上（实体与关系短语都有字符位置）；Extract像填报销单（生成三元组）；Verify像财务对票——每条报销项必须能在发票上找到对应文字，找不到就驳回；Supplement像最后对账，确认没有发票被漏贴（没有已锚定的span被丢弃）。这是对幻觉的系统性防御：LLM抽得“太热情”，锚定和验证把热情关进笼子。注意正文原话：它是2026年一个来源的设计，不是业界统一标准。与[第25课](<25：实体链接与消歧——候选、上下文、知识库与NIL.md>)的“候选验证”一脉相承——那边验证“输出的ID合法”，这边验证“输出的三元组有出处”，都是给生成模型套上确定性闸门。

图谱事实应带doc_id、offset、引文、版本、抽取器、时间限定和审核状态。原课涉及在任CEO的例句仅作语料，不作为当前人物职位事实。

（补充 2026-11-06）“在任CEO”的例子值得展开成时间边界一课：句子“Tim Cook是苹果CEO”为真只对某个时间区间成立——2005年为假、2011年8月之后为真。把无时间的事实写进图，等于宣称它永远为真，之后查询者无法判断“现在还是吗”。Wikidata的解法是qualifier：P169挂P580（起始时间）/P582（结束时间）。同理“就职于”边该带起始时间，“离任”是同一条边补结束时间，而不是删边——图要保留历史，删除会摧毁审计能力。这也是零节0.3第四步“边的档案”里放时间字段的原因：一条边的完整身份=两个端点+方向+出处+时间边界，缺任何一样，这条边都无法被信任地使用。

### 2.9 用一个小例子把概念串起来（补充）

合成句Bob founded Beta对应开放关系(Bob,founded,Beta)。若映射Wikidata P112，应得到(Beta,P112,Bob)，方向反转。只把relation字符串换成P112会产生格式正确、语义反向的图。这类问题不是增大模型就能自动消除，需要本体契约和单测。

## 四、Build It：原课分步代码与中文讲解

### 4.1 规则关系模板

PATTERNS仅演示单词大写姓名，不能识别完整Tim Cook或多词机构。\w、大小写与语言都限制匹配；否定或跨句代词更需额外处理。它没有定义extract，下一节补齐。

~~~python
PATTERNS = [
    (r"(?P<s>[A-Z]\w+) (?:is|was) (?:a|an|the) (?P<o>[A-Z]?\w+)", "isA"),
    (r"(?P<s>[A-Z]\w+) (?:is|was) born in (?P<o>\w+)", "bornIn"),
    (r"(?P<s>[A-Z]\w+) works? (?:at|for) (?P<o>[A-Z]\w+)", "worksAt"),
    (r"(?P<s>[A-Z]\w+) founded (?P<o>[A-Z]\w+)", "founded"),
]
~~~

### 4.2 REBEL生成关系

模型输出带<triplet>/<subj>/<obj>等标记，保留special tokens是为了按协议解析。需要校验生成实体与源文、去重及空输出，不可把预训练Wikipedia效果当领域性能。

~~~python
from transformers import AutoTokenizer, AutoModelForSeq2SeqLM

tok = AutoTokenizer.from_pretrained("Babelscape/rebel-large")
model = AutoModelForSeq2SeqLM.from_pretrained("Babelscape/rebel-large")

text = "Tim Cook was born in Alabama. He later became CEO of Apple."
encoded = tok(text, return_tensors="pt", truncation=True)
output = model.generate(**encoded, max_length=200)
decoded = tok.batch_decode(output, skip_special_tokens=False)
~~~

### 4.3 LLM锚定实体跨度

原prompt只要求subject/object的span，没有关系phrase的span，也不保证每条关系由原文支持。应补关系证据、否定/模态和文本归属校验。text[start:end]==entity只属于第一道检查。

~~~python
prompt = f"""Extract (subject, relation, object) triples from the text.
For each triple, include the exact character span in the source text.

Text: {text}

Output JSON:
[{{"subject": {{"text": "...", "span": [start, end]}},
   "relation": "...",
   "object": {{"text": "...", "span": [start, end]}}}}, ...]

Only include triples fully supported by the text. No inference beyond what is stated.
"""
~~~

### 4.4 规范关系ID及方向

原map把is the CEO of映射P169、founded映射P112，但二者在这些自然语言方向下都需反转：公司P169人；组织P112创始人。原字典只有小写前.strip输入，CEO大写key永远对不上，需要统一key。

~~~python
RELATION_MAP = {
    "is the CEO of": "P169",       # "chief executive officer"
    "was born in":   "P19",         # "place of birth"
    "founded":        "P112",       # "founded by" (inverted subject/object)
    "works at":       "P108",       # "employer"
}


# 原函数只返回关系ID，且key大小写不一致；请看补充方向修正。
def canonicalize(relation):
    rel_low = relation.lower().strip()
    if rel_low in RELATION_MAP:
        return RELATION_MAP[rel_low]
    return None   # drop unmapped open relations or route to manual review
~~~

### 4.5 建邻接表并查询

原extract未定义，原regex也匹配不出完整Tim Cook；未做规范化就查询P108，注释中的结果并不由代码保证。补充入口明确将worksAt→P108，建立可验证的toy图。

~~~python
triples = extract(text)
graph = {}
for s, r, o in triples:
    graph.setdefault(s, []).append((r, o))


# 仅查询当前graph，输出取决于前面实际抽取与规范化结果。
def neighbors(node, relation=None):
    return [(r, o) for r, o in graph.get(node, []) if relation is None or r == relation]


print(neighbors("Tim Cook", relation="P108"))    # -> [(P108, Apple)]
~~~

## 五、把代码运行起来：补充入口与检查

补充：运行原PATTERNS之后，加入教学extract与本体方向处理：
~~~python
import re

def extract(text):
    found = []
    for pattern, relation in PATTERNS:
        for match in re.finditer(pattern, text):
            found.append((match.group("s"), relation, match.group("o")))
    return found

def canonical_triple(subject, relation, obj):
    relation = relation.lower().strip()
    if relation in {"founded", "is the ceo of"}:
        return (obj, "P112" if relation == "founded" else "P169", subject)
    forward = {"worksat": "P108", "works at": "P108", "was born in": "P19"}
    if relation in forward:
        return (subject, forward[relation], obj)
    return None

raw = extract("Alice works at Acme. Bob founded Beta.")
normalized = [canonical_triple(*triple) for triple in raw]
normalized = [triple for triple in normalized if triple is not None]
assert ("Alice", "P108", "Acme") in normalized
assert ("Beta", "P112", "Bob") in normalized
print(normalized)
~~~
这些都是合成句，不是现实事实。修正依据：[Wikidata P169](https://www.wikidata.org/wiki/Property:P169)、[P112](https://www.wikidata.org/wiki/Property:P112)。本次不运行神经模型或加载外部图数据库。

简单规则适合窄模板；REBEL可做开源基线；领域数据可监督微调；审计场景可采用多步锚定与语义复核。规范后再进RDF/属性图，保存证据与时间。NER→coref→EL→RE→本体映射是可选集成顺序，不要求所有联合模型都拆成这些阶段。



## 七、失败模式、原文边界与工程注意

1. 字符锚点验证不等于关系语义验证，“Alice did not found Acme”即使两名都出现也不能抽正向创立。
2. P169/P112方向反转和canonicalize大小写不一致都需修正，不能仅返回关系ID。
3. 主体、省略、指代与跨句关系在toy正则里未实现。
4. 同名归一、关系同义、时间变化与事实冲突都需要保留来源，不直接覆盖。
5. source extraction precision/recall与规范化/链接准确率应分阶段测。
6. 原文“60%～80%工程时间”仅经验描述，不是任务分配公式。
7. 自动补覆盖可能引入新错误，补充结果仍要重复验证。

## 九、Exercises：保留原课练习与验收方法

1. Easy：5条新闻句跑规则，手工计算precision并记录无匹配句；也试多词姓名与否定以认识边界。
2. Medium：同句用REBEL/小LLM，建立完整gold后比较precision和recall，不能只比较抽出多少条。
3. Hard：50句上实施抽取+span验证+语义核验，比较过滤前后幻觉/错误率，报告假过滤导致的召回下降。
