### 0.1 先理解这一课在做什么

盖楼之前先画图纸：哪个房间承重、水电从哪走、预算多少。这一课就是给机器学习项目“画图纸”：模型只是大楼里的一个房间，真正决定成败的是**预测什么、谁根据预测做什么动作、多少钱、坏了怎么办**。原文讲了一个故事：一个 AUC 0.91 的流失模型上线三个月没人用——不是因为算法差，而是没人定分数触发什么动作、标签表里混进了“答案”、也没人拿它和“两周没活动就打电话”这条老规则比过。这些全是训练开始前就该发现的设计错误。

### 0.2 本课术语先翻成白话

- ML 任务=预测目标+实体+时间视野+用这个预测的决策，四样缺一不可
- 离线指标（offline metric）=上线前在留出的历史数据上算的分数
- 在线指标（online metric）=上线后在真实流量上量到的数字
- 业务指标（business metric）=决策真正要改变的公司结果，靠实验衡量
- 护栏指标（guardrail metric）=新模型上线时“不许变坏”的红线，如 p99 延迟
- 基线（baseline）=模型必须打败的对手：平凡基线、规则基线、现有系统
- 批量推理（batch inference）=定时任务给所有实体算好分数存表，请求时查表
- 在线推理（online inference）=请求来了才现场算分数
- 影子部署（shadow）=新模型只抄送流量算分、不参与决策，先看看表现
- 金丝雀发布（canary）=新模型只给 1-5% 流量做真实决策，随时回滚
- A/B 测试=随机分流，用统计检验比较两个版本的业务指标
- 反馈回路（feedback loop）=模型的决策改变了训练下一版模型的数据
- p99 延迟=100 个请求里 99 个都能低于这个耗时

### 0.3 用小数字走一遍

在线推理报价（可手算，与原课参考输出一致）：峰值 40 QPS，每个副本扛 200 QPS，则 `ceil(40/200)=1`，但可用性要求至少 2 个副本，取 `max(2,1)=2`；每副本 $0.50/小时，一天 24 小时 → 2 × 0.50 × 24 = **$24.00/天**。

Little 定律（原文：在途请求数 = 吞吐 × 延迟）：400 请求/秒 × 50 毫秒 = 400 × 0.05 = **20 个**请求任意时刻在处理中。

批量推理的算式：若最大过期时间为 25 小时、批任务跑 1 小时，则刷新间隔 = 25 − 1 = 24 小时，每天跑 1 次；200 万实体 × 1 次 = 200 万次预测，按 $0.40/百万计为 $0.80/天，再加读取费（原课参考输出合计 $0.91/天）。

以上是用于理解的算例，不是新增的训练或性能实测。

### 0.5 理解检查（含参考答案）

**问题1：** AUC 0.91 的模型为什么可能没人用？

**参考答案：** AUC 只说明分数在历史数据上排序能力强，不说明有人根据分数行动。若没人定义“分数高到多少触发什么动作”、分数到达频率和业务节奏不匹配、或特征里混了泄漏，模型再准也进不了业务流程。

**问题2：** 离线指标和业务指标为什么会不一致？

**参考答案：** 离线指标在历史数据上算，而历史数据里没有你的模型在干预；业务指标衡量决策对真实世界的影响，还混着公司其他一切因素。所以要分三层（离线/在线/业务）加护栏，而不是指望一个分数代表一切。

**问题3：** 影子部署和金丝雀有什么区别？

**参考答案：** 影子模型只接收流量副本、输出只记日志不生效，用于上线前对表现；金丝雀让新模型对一小部分流量做真实决策，出问题按预案回滚。影子在前、金丝雀在后。

## 一、这一课解决什么问题？

订阅公司要“一个流失模型”。数据科学家训练了梯度提升分类器，报告 AUC 0.91。三个月后没人用它。原因与算法无关：没人决定分数触发什么动作；分数每周才来一次，而挽留团队每天都要打电话；标签来自一张还存着“取消原因”的注销表，于是某个特征直接包含了答案；也没人把模型和客服团队的老规则（“两周没活动就打电话”）比较过。原文的结论：这些失败都发生在训练开始之前，是设计失败；一页设计文档就能在事前问出每一个。这一课教你写这份文档：把业务目标翻译成 ML 任务、分清四层指标、给批量/在线服务定价、选发布模式、识别反馈回路，最后用检查清单给设计文档打分。

## 二、核心概念与推导

### 2.1 从业务目标到 ML 任务

业务目标不是 ML 任务，用四个问题翻译：

1. 模型到底预测什么、对哪个实体（用户、支付、门店、商品）？
2. 哪个决策使用这个预测、谁做这个决策？
3. 预测什么时候需要？那一刻存在哪些数据？
4. 怎么知道决策变好了？

| 业务目标 | 预测 | 使用预测的决策 | ML 任务 |
|---|---|---|---|
| 减少流失 | 用户未来30天取消的概率 | 每晚给前5%发挽留优惠 | 二分类 |
| 减少欺诈损失 | 这笔支付是欺诈的概率 | 100毫秒内批准/人工/拒绝 | 二分类 |
| 货架不缺货 | 每店每日下周销量 | 每店订货量 | 预测（回归） |
| 展示相关内容 | (用户，商品) 的相关性分数 | 信息流排序 | 排序 |

第二列最要小心：“预测流失”把视野、实体、动作全留着空白；“预测该用户未来30天是否取消、供今晚的定时任务决定谁拿优惠”把三样都钉死了。

### 2.2 什么时候不该用机器学习

Google《Rules of Machine Learning》的第一条就是：不要害怕发布没有机器学习的产品。下列情况别上 ML：一条短规则就能达到目标并保持正确（规则更便宜、好测试、好解释）；没有标签也没有可行的收集办法；没人根据预测行动，预测再准也不改变什么；预测时刻存在的数据里没有信号；单个错误不可接受且无人能复核；系统的建设与运行成本超过更优决策的价值。当规则变得又长又脆，ML 才开始划算——同一指南第3条倾向用可学习的模型替代复杂启发式，因为模型更容易更新维护。

### 2.3 指标的三层，加护栏

| 层 | 什么时候能量 | 流失示例 |
|---|---|---|
| 离线指标 | 上线前，留出的历史数据 | 优惠阈值处的 F1、前5%的精确率 |
| 在线指标 | 上线时，真实流量 | 优惠接受率、被打分的用户占比、分数分布 |
| 业务指标 | 上线数周后，靠实验 | 实验组 vs 留存对照组的30天流失率 |
| 护栏指标 | 一直看 | 每挽留一个用户的优惠成本、退订率、p99 延迟 |

三层经常不一致：离线指标给历史打分，而历史里没有你的模型；在线指标取决于人对决策的反应；业务指标动得慢、噪声大。选离线指标要贴着决策选：任务联系前5%用户，就量前5%的精确率——AUC 对所有阈值求平均，包括你永远不会用的阈值（核对：这是原文观点，用于解释为什么 AUC 不总是对的离线指标）。Google 指南第2条：先设计和实现指标，再决定 ML 系统做什么。

### 2.4 基线：分数没有上下文就没有意义

F1=0.56，如果最强替代方案只有 0.30 就是好，如果一条规则能到 0.60 就是差。每个模型和三类基线比：

- **平凡基线（trivial）**：永远预测多数类，或永远预测训练均值。
- **规则基线（heuristic）**：来自领域知识的一条规则，或训练数据上拟合的单特征阈值。
- **现有系统**：今天实际做这个决策的东西，哪怕是一个拿着表格的人。

**提升（lift）**= 模型分数 − 最强基线的分数。看结果之前先定最小提升，且要大到足以支付整个系统的额外成本。平凡基线通常很弱，规则基线才是难缠的对手。

### 2.5 数据与标签要求

训练前回答：**标签来源**（哪张表/哪个事件定义标签、谁拥有）；**标签延迟**（预测后多久真相才到——欺诈拒付可能几周后才来，流失标签要等30天视野走完）；**标签质量**（谁打的、多常打错）；**预测时刻可用性**（每个特征在预测那一刻存在吗？系统在结果之后才写入的特征会把标签泄漏进训练）；**每类样本量**（只有200个正样本就别上复杂模型）；**时间切分**（留出最近的一段，理由同[第15课](<15：时间序列——平稳性、滞后特征与滚动验证.md>)）。

### 2.6 延迟、吞吐与成本预算

三个数框住一切服务设计：**延迟预算**（p99 延迟——99%请求低于的耗时；支付检查可能要50ms，夜间报表可以几小时）；**峰值吞吐**（按最忙的一分钟配系统，不是日均；峰值 QPS 常数倍于均值）；**成本预算**（写成每天多少美元或每千次预测多少美元，方便比较方案）。

Little 定律把前两个连起来：

$$L = \lambda \times W$$

在途请求数 = 吞吐 × 延迟。400 请求/秒、每个 50ms，则任意时刻 20 个请求在处理中。

### 2.7 批量推理 vs 在线推理

- **批量推理**：定时任务给每个实体算分、写进表或键值库；应用请求时读现成分。
- **在线推理**：应用在请求时把特征发给模型服务，等分数回来。

| 属性 | 批量 | 在线 |
|---|---|---|
| 新鲜度 | 上次运行那么旧（加运行时长） | 用请求时刻的数据 |
| 请求延迟 | 一次键值读取，几毫秒 | 特征拉取加模型耗时 |
| 成本驱动 | 实体数 × 每天运行次数 | 按峰值 QPS 配的副本数 |
| 新实体 | 下次运行前没有分数 | 第一个请求就打分 |
| 坏的时候 | 旧分数还能读 | 请求失败或超时 |

批量成本随实体数和运行次数增长：过期时间越短、跑得越勤；一个要跑1小时的批任务无论花多少钱都满足不了1小时以内的过期限制。在线成本随峰值走，因为你要为峰谷之间的空闲副本付钱。混合设计很常见：夜间批量给老用户打分，在线路径给新用户和需要新鲜数据的请求打分。

### 2.8 部署模式：影子、金丝雀、A/B

新模型分阶段触达用户：**影子**——新模型接收线上流量副本，只记日志不生效，对比延迟、错误率、预测分布；**金丝雀**——新模型对 1-5% 流量做真实决策，逐步放量，护栏一破就回滚；**A/B 测试**——用户随机分组看两个版本，用统计检验量业务指标，需要足够流量与时间。每个阶段都要有“几分钟内能完成”的回滚：保留旧版本在线，用配置切流量。

### 2.9 反馈回路：模型改变自己的教材

反馈回路指模型的决策改变了训练下一版模型的数据（Sculley 等人把它列为 ML 技术债的主要来源）。三种常见情形：**干预隐藏标签**——流失模型发优惠、优惠留住了人，下个月高危用户看起来很忠诚，重训练的模型就学到“这些特征不预测流失”；**被拦的动作没有结局**——欺诈模型拦下支付，那笔支付永远不会有拒付标签，重训练时被拦区域的正例越来越少；**曝光限制反馈**——排序模型只展示头部商品，只有头部商品能收集到点击。解法共一个思路：保留一小撮模型没影响过的数据。留出永远不受干预的随机小组；给一小部分流量随机决策；每个样本记录分数与决策，让后续训练能区分“被影响的数据”与“干净数据”。

### 2.10 失败模式与安全默认

每个部件早晚出问题。默认动作要在设计阶段定好，不是事故现场定：

| 失败 | 没预案的后果 | 安全默认 |
|---|---|---|
| 模型服务超时 | 请求失败 | 用规则基线 |
| 夜间批任务失败 | 分数缺失或过期 | 限时内沿用上次好分数，超时用规则 |
| 特征缺失或越界 | 模型吃坏输入打分 | 用文档写明的默认值并记录事件 |
| 新实体没有历史 | 没有分数 | 用规则或总体均值 |
| 分数分布突然移动 | 规模化错误决策 | 暂停自动动作、报警给人 |

指标那节的规则基线同时就是大多数失败的兜底，所以先把它建好。

### 2.11 设计文档与检查清单

设计文档把上述决策在训练开始前写在一处。六个项是“阻塞项”（不过就不该评审，因为每一项缺失都会让系统不安全或没用）：**决策**（problem.decision）、**业务指标**、**启发式或现有系统基线**、**无泄漏**（每个特征预测时刻可得）、**影子或金丝雀加回滚**、**每个失败都有默认动作**。非阻塞项：服务模式匹配预算、反馈回路对策、上线后监控。

### 2.12 用一个小例子把概念串起来（补充）

把流失故事按本课流程走一遍：第一步定任务——“预测该用户未来30天是否取消（二分类），供每晚批量任务挑前5%发优惠”，实体=用户，决策=发优惠，频率=每晚，匹配业务节奏。第二步选指标——离线：前5%精确率（贴决策，不用 AUC 一刀切）；护栏：每挽留用户的优惠成本、p99 延迟；业务：实验组 vs 对照组30天流失率。第三步定基线——平凡（多数类）、规则（“闲置>14天就打电话”）、现有系统（客服现在的做法），先定“提升至少0.05才值得建系统”。第四步查数据——标签来自注销表但**去掉取消原因字段**（防泄漏），标签延迟30天，写明每个特征的预测时刻可用性。第五步算预算——每晚跑一次、200万实体 → 批量便宜（$0.91/天，原课参考）；新鲜度要求24小时以上，批量够用。第六步上线——影子两周对分布，金丝雀1%起步、护栏破就回滚，同时留一个永远不发优惠的5%对照组保住干净标签。第七步写检查清单——六个阻塞项逐项打勾，`review_design_doc` 达 0.85 且无阻塞失败才进评审。这个流程就是本课全部概念的一次排队走动。

### 4.1 第一步：描述工作负载与价格

`Workload` 装流量数字与预算，`CostModel` 装价格。原文强调：价格是练习用的整数，不是厂商报价。

~~~python
# 本块中文说明：工作负载（流量与预算）和成本模型（价格）两个数据类。
@dataclass(frozen=True)
class Workload:
    name: str
    entities: int
    requests_per_day: int
    peak_qps: float
    max_staleness_hours: float
    latency_budget_ms: float


@dataclass(frozen=True)
class CostModel:
    batch_dollars_per_million: float = 0.40
    batch_job_hours: float = 1.0
    lookup_dollars_per_million: float = 0.25
    lookup_latency_ms: float = 4.0
    replica_dollars_per_hour: float = 0.50
    replica_qps: float = 200.0
    min_replicas: int = 2
    online_latency_ms: float = 35.0
~~~

### 4.2 第二步：给批量和在线服务定价

批量的核心约束：任务必须跑进过期时限内，两次运行的间隔 = 时限 − 任务时长；每次运行给**所有**实体打分，不管有没有人来查。

~~~python
# 本块中文说明：批量方案报价：过期时限减任务时长得到刷新间隔，再算每天运行次数与总费用。
def batch_plan(workload: Workload, costs: CostModel) -> ServingPlan:
    refresh_hours = workload.max_staleness_hours - costs.batch_job_hours
    if refresh_hours <= 0:
        return ServingPlan(
            "batch", False, math.inf, costs.lookup_latency_ms, math.inf, 0.0,
            "staleness limit is shorter than one batch job",
        )
    runs_per_day = 24.0 / refresh_hours
    predictions = workload.entities * runs_per_day
    dollars = (
        predictions / 1e6 * costs.batch_dollars_per_million
        + workload.requests_per_day / 1e6 * costs.lookup_dollars_per_million
    )
    ...
~~~

在线方案为峰值配副本，可用性至少两个：

~~~python
# 本块中文说明：在线方案报价：按峰值 QPS 除以单副本能力向上取整，保底两个副本。
def online_plan(workload: Workload, costs: CostModel) -> ServingPlan:
    replicas = max(costs.min_replicas, math.ceil(workload.peak_qps / costs.replica_qps))
    dollars = replicas * costs.replica_dollars_per_hour * 24.0
    feasible = costs.online_latency_ms <= workload.latency_budget_ms
    ...
~~~

`choose_serving`（原文未给出代码）保留同时满足延迟与过期限制的方案、返回最便宜的一个；都不满足时返回 `None`，提示你回去改预算。

### 4.3 第三步：模型对基线的比较

同一个指标给模型和每个基线打分，和**最强**基线比提升。`higher_is_better=False` 时（如误差类指标）用 min 选基线、方向反过来。

~~~python
# 本块中文说明：用同一指标给模型与全部基线打分，报告对最强基线的提升。
def compare_to_baselines(
    y_true: list,
    model_pred: list,
    baselines: dict[str, list],
    metric,
    metric_name: str,
    higher_is_better: bool = True,
    min_lift: float = 0.02,
) -> BaselineReport:
    if not baselines:
        raise ValueError("a model needs at least one baseline")
    scores = {name: metric(y_true, pred) for name, pred in baselines.items()}
    pick = max if higher_is_better else min
    best_name = pick(scores, key=scores.get)
    model_score = metric(y_true, model_pred)
    lift = model_score - scores[best_name] if higher_is_better else scores[best_name] - model_score
    return BaselineReport(metric_name, {"model": model_score, **scores}, best_name, lift, min_lift)
~~~

原文说明：规则基线是单特征规则，`fit_rule`（原文未给出代码）在训练数据上逐个尝试特征值当阈值、保留 F1 最好的那个；演示在合成流失数据上训练一个小逻辑回归并与三个基线比较。

# 本块中文说明：补充 BaselineReport 最小定义，并用小数据核对基线比较逻辑。
from dataclasses import dataclass


@dataclass(frozen=True)
class BaselineReport:
    metric_name: str
    scores: dict
    best_baseline: str
    lift: float
    min_lift: float


def accuracy(y_true, y_pred):
    return sum(t == p for t, p in zip(y_true, y_pred)) / len(y_true)


y_true = [1, 1, 0, 0]
report = compare_to_baselines(
    y_true,
    model_pred=[1, 0, 0, 0],                      # 对 3 个
    baselines={"majority": [0, 0, 0, 0]},        # 对 2 个
    metric=accuracy,
    metric_name="accuracy",
    min_lift=0.1,
)
# 可手算预期：model 0.75，majority 0.50，lift 0.25

## 七、失败模式、原文边界与工程注意

1. 成本模型里的价格是“练习用的整数”，不是厂商报价；结论用于比较方案，不用于报预算（核对：原文明说 round numbers for the exercise）。
2. 0.85 的文档得分线与“六个阻塞项”是本课的约定，不是行业标准；你可以调，但每个阻塞项的理由（缺失即不安全或没用）仍然成立。
3. AUC 覆盖你不会用的阈值，不必然匹配决策；贴决策选指标是原则，具体选哪个要回到任务。
4. “模型赢了基线 0.064 所以值得部署”只在演示数据上成立；换数据规则可能赢，那时规则就是正确的系统。
5. 反馈回路的对策（留对照组、随机小流量、记录分数与决策）都会损失短期收益，要在设计阶段就算进成本。
6. 一个跑1小时的批任务永远满足不了1小时以内的过期时限——先改预算或换在线，别试图“优化批任务”。
7. 在线副本按峰值配，意味着低谷时在为空闲付钱；流量波动大的业务混合方案常更省（原课练习1要求自己实现混合方案，因为本课代码没有）。
8. 回滚必须“分钟级”：旧版本保持在线、配置切流量。等到事故现场再想回滚就是设计失败。
9. 设计文档检查器没有检查“标签来源是否真的可信”，它只检查你写了什么；文档写得漂亮不等于数据没问题。

## 十、术语与完成标准

ML 任务：预测目标+实体+视野+决策的四元组；离线/在线/业务/护栏指标：分别在历史数据、真实流量、实验、全程红线处量的数；基线：平凡、规则或现有系统的对照；批量/在线推理：预计算存表查读 vs 请求时现算；影子/金丝雀/A-B：不生效→小流量生效→随机分流的发布三段；反馈回路：模型决策改变其未来训练数据；lift：对最强基线的分数差。

完成检查：

- 能把“减少流失”翻译成含实体、视野、决策的 ML 任务。
- 能说出三层指标各在什么时候量、为什么经常不一致。
- 能用 Little 定律手算在途请求数，并用副本算式报出在线方案日成本。
- 能解释为什么一条1小时的批任务满足不了1小时内的过期时限。
- 能列出反馈回路的三种情形与共同解法。
- 能对一份设计文档指出六个阻塞项缺了哪个。
