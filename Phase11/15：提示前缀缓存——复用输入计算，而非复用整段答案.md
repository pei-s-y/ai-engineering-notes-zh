## 一、为什么相同提示还需要再次发送

一个会话每轮包含同样的系统规则、工具 schema 和固定文档。服务商可能复用这些前缀的中间计算，减少重复处理成本，但模型仍要读取本次新问题并生成答案。

**Prefix 前缀**是从输入开始连续相同的一段。**KV cache** 是注意力中间的 key/value 表示；提供商提示缓存把输入处理结果作为可复用资源。应用仍按 API 约定提供输入，不能因为“上次发过”就省掉规则，除非使用明确的服务器状态/缓存对象接口。

第11课答案缓存可以不调用生成模型；本课缓存命中后仍有后续输入、输出和可能的推理费用。

## 二、前缀匹配的直觉例子

```text
请求甲：固定规则 | 固定工具 | 固定资料 | 问题：退款多久？
请求乙：固定规则 | 固定工具 | 固定资料 | 问题：支持什么支付？
```

前面稳定部分有复用机会。如果最开头加每次变化的时间戳，匹配很早就断掉。后面再相同也不等于能自动接着复用全部。相同语义但不同文字不是相同 token 前缀。

稳定布局一般为：规则→稳定工具定义→固定示例/资料→动态历史、检索与本次问题。但消息角色、业务正确性和指令优先级必须保持，不应为命中率把不可信资料升级为高优先级指令。

工具序列化要稳定，JSON 键序、列表顺序、版本变动都可能影响匹配。部分缓存可命中之前的共同前缀，不是“任一字节不同整个请求全部失效”。跨提供商不会共享同一份 KV；布局相似不等于缓存互通。

## 三、写、读、未命中、TTL 与费用

**Cache write** 第一次建立缓存；**read** 重用；**TTL** 有效期；过期可能重新写。有效期是固定、滑动刷新还是尽力保留要按服务约定，不能只用“能缓存一小时”概括。

设一次普通前缀成本为 B，写入倍率 w，读倍率 r，总使用 n 次且一次写、n−1次读：

`缓存前缀成本 = B[w+(n−1)r]`

`不缓存成本 = Bn`

省钱条件：`w+(n−1)r<n`。演示 w=1.25、r=0.1：两次共1.35B，平均0.675B，省32.5%；11次共2.25B，平均约0.2045B，省79.55%。w=2、r=0.1时，两次2.1B还不省，三次2.2B低于3B，需要至少两次读。

如果还有动态输入、输出和存储费用，要加回总账；80%前缀折扣不等于整个应用便宜80%。

## 四、原文提供商对照与核对说明

原课展示 Anthropic cache_control、OpenAI 前缀缓存、Gemini CachedContent 三种接口思路。固定折扣、最低长度、TTL、模型支持都不能泛化到所有当前模型。

- Anthropic 的显式标记描述缓存边界；原课 5 分钟写入1.25倍/读0.1倍、1小时写入2倍可用于理解盈亏计算。但原文后面把1小时写入说成“50%溢价”，与2倍相矛盾，应按2倍=100%溢价理解该示例。最低长度随模型变化。[官方缓存说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- OpenAI 原课“自动、无可配置项、统一50%”并非通用当前规则。官方目前区分支持模型与自动/显式缓存相关选项；实际核对请求模式及返回缓存用量，不硬编码统一折扣或保留时间。[官方提示缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)
- Gemini 不只有显式缓存。官方说明存在隐式缓存；当前 Interactions API 不支持手动缓存对象，显式缓存是否可用依模型与 generateContent 接口。[官方上下文缓存说明](https://ai.google.dev/gemini-api/docs/caching)

这些核对用于避免照旧表误操作；学习重点仍是相同前缀、输入计算复用、usage验证和账单模型。

### 步骤 1：显式缓存边界

Anthropic原课例子标记稳定内容块；检查cache creation/read usage而不是凭速度猜。接口片段未实测，具体模型阈值看官方支持范围。

````python
# 本块中文说明：显式缓存边界
import anthropic

client = anthropic.Anthropic()

SYSTEM = [
    {
        "type": "text",
        "text": "You are a senior Python reviewer. Follow the rubric exactly.\n\n" + RUBRIC_15K_TOKENS,
        "cache_control": {"type": "ephemeral"},
    }
]

def review(code: str):
    return client.messages.create(
        model="claude-opus-4-7",
        max_tokens=1024,
        system=SYSTEM,
        messages=[{"role": "user", "content": code}],
    )
````

````python
# 本块中文说明：显式缓存边界
response = review(code_a)
response.usage
# InputTokensUsage(
#     input_tokens=120,
#     cache_creation_input_tokens=15023,   # paid at 1.25x
#     cache_read_input_tokens=0,
#     output_tokens=340,
# )

response_b = review(code_b)
response_b.usage
# cache_creation_input_tokens=0
# cache_read_input_tokens=15023           # paid at 0.1x
````

显式CachedContent按对象引用复用输入，适用模型/API受限；新接口也有隐式缓存，不要混用旧google.generativeai与新SDK对象。

````python
client = genai.Client()

cache = client.caches.create(
    model="gemini-3.8-flash",
    config=types.CreateCachedContentConfig(
        display_name="rubric-v3",
        system_instruction=RUBRIC,
        contents=[FEW_SHOT_EXAMPLES],
        ttl="3600s",
    ),
)

resp = client.models.generate_content(
    model="gemini-3.8-flash",
    contents=["Review this code:\n" + code],
    config=types.GenerateContentConfig(cached_content=cache.name),
)
````

### 步骤 5：命中会计统计

实际可运行的离线模拟器在code/main.py，跟踪每请求prefix_key、写读次数与模拟价格。它不是与三家服务实测命中率的脚本。


## 六、离线模拟怎样读

在本课目录执行 `python code/main.py`，仅需标准库。脚本生成请求序列，按 prefix_key 模拟不同提供商的写/读/未命中与费用，并打印每1000请求混合费用。这不是向三家发送真实请求的测试。

`Request` 存前缀 token、后缀 token、前缀键；`CacheEntry` 存写入时间/TTL；`ProviderStats` 累计次数、输入费和存储费；`make_traffic` 产生有重复前缀的流量；`baseline_cost` 算不缓存对照。

核对：PRICES 的源码数字与正文表格不一致，作为演示参数而非真实价格。模拟器按写入时间过期，未必模拟了真实命中刷新；未覆盖最短 token 阈值、路由/逐出、分块/部分前缀命中、输出费等。不能把模拟命中率当线上命中率。

补充独立计算：

```python
def prefix_ratio(total_uses, write_multiplier, read_multiplier):
    assert total_uses >= 1
    return (write_multiplier + (total_uses-1)*read_multiplier) / total_uses

print(round(prefix_ratio(2, 1.25, 0.1), 4))   # 预期 0.675
print(round(prefix_ratio(11, 1.25, 0.1), 4))  # 预期 0.2045
```

## 七、怎么验证真实命中

固定版本与稳定前缀→预热→在有效期内发送仅后缀不同的请求→记录实际 usage 的缓存输入数、非缓存输入数、输出、时间→按服务商计费项算账。不要仅根据“第二次快了”推断缓存命中，网络和负载也会变化。

两个指标分开：命中请求数/请求数，缓存输入token/全部输入token。一个请求只命中很短前缀也可算请求命中，却省不了多少。CI 可检查布局和统计字段，但实际服务器缓存是否保留不是纯本地单测可保证。

常见失败：动态时间放太前、工具顺序变、内容版本漂移、前缀不足门槛、间隔太长、统计遗漏、把语义近似当精确匹配。先查这些，再调整缓存策略。
